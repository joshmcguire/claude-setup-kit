# CLAUDE.md (machine-wide working rules)

This file is the operating system for how Claude Code works on this machine. Project-specific
facts never live here; they live in each project folder. This file only says how to find them
and what the standard workflow is.

## Finding things (the routing chain)

1. **All projects live in `~/projects/`.** The index is **`~/projects.md`**: one table row per
   project with name, path, one-line description, and onboarding link. When a project is
   mentioned, look it up there first. The index is **generated** from each project's
   ONBOARDING.md frontmatter by `project-index`; never hand-edit it, fix the frontmatter
   and regenerate.
2. **Inside a project, read in this order at session start:**
   - `CLAUDE.md` (how we work on this project, hard rules, tech stack)
   - last ~10 entries of `CHANGELOG.md` (where we left off)
3. **Before any architectural choice:** read `docs/PRINCIPLES.md` (the project's north star),
   then `grep decisions/` and read the relevant ADRs. Only `status: active` records are binding.
4. **Order of authority when files disagree:**
   `docs/PRINCIPLES.md` (why) → `decisions/` (what was decided) → `CLAUDE.md` (how we work) →
   `ONBOARDING.md` (orientation only; may lag, trust the others).

## Context discipline (keep sessions lean)

- Index lines route; deep files load on trigger. Read ONBOARDING's "When to read deeper"
  list and pull a deep doc only when its trigger matches the task at hand. Reading everything
  "to be safe" dilutes attention and makes answers worse, not better.
- For broad reading (audits, "understand X", anything touching many files), delegate to an
  Explore subagent and keep the conclusions; do not fill the main context with file dumps.
- Never add "how to use this file" meta-headers inside deep docs. A file describes itself in
  one frontmatter/description line; the indexes are generated from those (`project-index`,
  `adr-index`). A summary stated twice is a summary that rots.

## Standard project structure

Every project folder contains:

```
CLAUDE.md            # thin: what it is, stack, hard rules, pointers (1 page max)
ONBOARDING.md        # orientation for a cold start: what, why, how to run
CHANGELOG.md         # append-only: - **YYYY-MM-DD** — what changed and why
LEARNINGS.md         # append-only: operational gotchas (not decisions, not history)
docs/PRINCIPLES.md   # mission + non-negotiable values for THIS project
decisions/           # ADRs: NNNN-slug.md + README.md index (the architecture of record)
transcripts/         # dated meeting/voice notes: YYYY-MM-DD-topic.md (mined for decisions)
```

- **New project: run `new-project <slug> "Name" "one-line description"`.** It scaffolds
  the structure from `~/templates/project/` and registers it in `~/projects.md`. Registration
  is mandatory, no exceptions, even for throwaway experiments (mark them as such in the
  description).
- **File ownership (prevents drift):** CLAUDE.md = rules only, no codebase facts, ~80 lines
  max. ONBOARDING.md = facts + the index frontmatter (name/description/status). PRINCIPLES =
  values. CHANGELOG = history. LEARNINGS = operational gotchas (the trap + the rule that avoids
  it; not decisions, not history). A fact stated twice is a fact that rots; pick its one home.
- **Superseding a project:** set `status: superseded by <slug>` in the old project's
  ONBOARDING frontmatter, add a one-line banner at the top of its CLAUDE.md pointing to the
  replacement, run `project-index`.
- If asked to work in a project missing pieces of this structure, scaffold the missing pieces
  first, then do the work.
- `project-doctor` reports drift (missing files, stale changelogs, draft ADRs, fat
  CLAUDE.md files, setup-kit drift). Run it when asked for a health check, or weekly.

## ADR protocol (full format: `decisions/README.md` in each project)

- New decision: `new-adr <slug>`. The index table in `decisions/README.md` is
  regenerated by `adr-index`; never hand-edit either the numbering or the table.
- Never edit a superseded record's substance: write a new ADR, flip the old one's status to
  `superseded by NNNN`, add a one-line pointer at the top of its body.
- A decision that needs the user's sign-off gets `status: draft`; the session-start hook
  surfaces lingering drafts until they are promoted or dropped.
- Write an ADR whenever a choice would be expensive to reverse or someone might re-litigate it:
  a dependency, a data model, a protocol, a hosting/deploy assumption, a "we tried X, never again".

## Git, issues, branches (per project once it has a remote)

- **Pre-deploy / solo phase:** commit straight to `main`; branch ad-hoc for anything risky.
- **Post-deploy:** branch-per-issue → PR → preview/CI → merge. `main` stays deployable.
- **Issue triage for every request (assume the user never opens issues themselves):**
  1. An existing backlog issue fits → reuse it, branch `feat/<#>-slug`.
  2. A substantial new ask → auto-create the issue (title + brief body), say what was filed,
     then branch it.
  3. A trivial one-off (typo, copy, tiny style) → skip the issue, small branch + PR.
- PR bodies use `Closes #<#>` so merging closes the issue and advances the board.
- Commit policy is set per project in its CLAUDE.md (auto-commit at working checkpoints vs
  commit-on-request). Default if unstated: only commit when asked.

## Transcripts and decision mining

- Voice notes, meeting transcripts, and design discussions go in the project's `transcripts/`
  as `YYYY-MM-DD-topic.md`. Date prefix is mandatory; it is how mining knows what is new.
- **Whenever you read or add a transcript, check it for decisions** that should be promoted to
  an ADR or appended to the CHANGELOG. `mine-transcripts <project>` runs this as a batch
  over transcripts newer than the latest ADR.
- A transcript is raw material, never authority. If a transcript contradicts an active ADR,
  surface the conflict; do not silently follow the transcript.

## CHANGELOG

- Append `- **YYYY-MM-DD** — what changed and why` for every meaningful working session.
- If work is unfinished, end the latest entry with `NEXT: <the exact next step>`. The
  session-start hook prints it, so the next session resumes with zero digging.
- This is the resume-point for the next session. If it is not in the CHANGELOG, an ADR, or a
  commit, it did not happen.

## LEARNINGS

- When a non-obvious gotcha costs time (a tooling trap, a race, a "looked green but wasn't"),
  append it to the project's `LEARNINGS.md`: `- **YYYY-MM-DD** — the trap, then the rule that
  avoids it`. Newest on top. Do this without being asked; it is how mistakes stop recurring.
- LEARNINGS is for operational traps, not decisions (those are ADRs) or history (that is the
  CHANGELOG). Read it at session start alongside the CHANGELOG.

## Behavior

- Do the full job: run commands, fix failures, then report. Do not hand back commands to run.
- If something fails, try to fix it yourself before asking for help.
- Use `--noconfirm`, `-y`, and auto-accept flags where safe. Prefer things that just work over
  asking about options.
- Prompts arrive via voice-to-text; interpret intent, ignore typos.
- Be concise.

## Clear points

- Proactively offer a `/clear` at genuine boundaries (task finished and committed, or a
  design→code mode switch), never mid-task. At that boundary run the **`/clearpoint`** skill —
  it saves state (commit + CHANGELOG + any ADR + LEARNINGS) and emits the next-prompt block plus
  the plain-English "Before you clear" checklist. Don't paraphrase the ritual from memory; run it.

## Verify gate (per-project, opt-in)

- A live or otherwise high-stakes project can wire `claude-verify-gate` as a Stop hook in its
  `.claude/settings.json`: when source changed, the harness runs the project's typecheck + fast
  test itself before the session ends, so "tests pass" is confirmed, not asserted. Off by
  default; turn it on where a wrong green is expensive.
